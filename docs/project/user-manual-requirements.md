# 用户说明书编写要求

## 1. 文档定位

本说明书是面向最终用户的电子版用户手册，服务于碳盾 SOC-Shield 的安装、操作、结果理解和报告使用。

说明书不替代以下文档：

- `BUILD.md`：开发者构建与发布说明。
- `docs/project/architecture.md`：代码架构说明。
- `docs/project/logic-and-data-contract.md`：业务口径与计算契约。
- `docs/audit/`：逻辑审计和修复记录。

说明书不得以源码目录、类名、Provider、DAO、数据库表等内部实现概念作为用户操作主线。

## 2. 目标读者

说明书按以下读者的共同使用流程编写：

- 需要完成一次土壤有机碳评估的普通用户。
- 需要比较侵蚀处理、土层或历史记录的科研和技术人员。
- 需要生成 AI 中文分析报告或 PDF 报告的业务用户。

不以 Flutter、Dart、SQLite 或 API 开发人员为主要读者。

## 3. 成品结构

说明书由三个层次组成：

1. **快速入门**：用最少的概念讲清核心流程，使用户能够完成第一次评估。
2. **完整用户指南**：严谨覆盖页面、参数、结果、历史、报告、导入导出和故障处理。
3. **科学口径与附录**：集中说明公式、单位、数据来源、版本和模型限制。

辅助章节包括常见问题、术语表和版本记录。

## 4. 三部分的内容要求

### 4.1 快速入门

快速入门应围绕一条完整任务链组织：

```text
启动应用 -> 填写参数 -> 执行计算 -> 查看结果 -> 查看剖面/情景 -> 生成报告 -> 保存记录
```

必须覆盖：

- 应用解决的问题和适用场景。
- 施肥处理、侵蚀程度、土层和容重的基本含义。
- 一次默认或示例计算的完整操作。
- SOC、碳库、损失率和剖面结果的最基本解释。
- 如何生成 PDF、查看历史记录和恢复草稿。

快速入门不应展开全部公式，也不应先介绍内部技术实现。必要的科学限制用短提示呈现，并链接到科学附录。

### 4.2 完整用户指南

完整指南必须按用户任务和页面功能说明：

- 页面结构和主要入口。
- 每个参数的显示名称、单位、允许范围、默认值和是否参与核心计算。
- 计算失败、输入无效、网络失败和文件失败时的用户处理方式。
- 图表的数据含义、单位、适用比较方式和展示限制。
- AI 配置、流式生成、取消、错误和隐私注意事项。
- PDF 的生成、保存、分享、打开、缺失检测和删除行为。
- 历史记录的查看、重命名、参数载入、删除和多记录对比。
- JSON 导入导出的边界，以及不同算法版本的兼容提醒。
- Windows 与 Android 的平台差异。

### 4.3 科学口径与附录

科学附录必须与 `docs/project/logic-and-data-contract.md` 保持一致。至少包含：

- SOC 的三维查表键：施肥处理 × 侵蚀程度 × 土层键。
- `10/25/35/45/55` 与 `0-20/20-30/30-40/40-50/50-60cm` 的映射。
- 单层碳库和碳密度公式及单位。
- CK 的定义：同施肥、同土层、侵蚀 0cm。
- 0-20cm 与 0-60cm 剖面的连续覆盖要求。
- 秸秆碳输入和系统总碳输入公式。
- pH、含水量、黏粉粒和全氮当前仅为辅助观测参数。
- 算法版本、历史字段兼容和从历史载入后的重新计算规则。

必须明确说明：

> 当前应用计算的是当前侵蚀处理相对于同施肥、同土层、侵蚀 0cm CK 的静态差异。原始资料没有逐年末期值或可复现的动态模型参数，因此 20 年和 100 年字段不是动态预测。

## 5. 当前项目事实的统一口径

说明书使用以下当前事实，不得沿用旧版归档文档中的过时表述：

- 应用版本为 `1.1.5+3`，算法版本为 `v2`，数据库版本为 `v3`。
- 当前支持 Windows 和 Android。
- SOC 直接来自原始数据表，不由 pH、含水量、黏粉粒或全氮回归得到。
- F 与 UNF 是两套独立数据，不叠加额外施肥系数。
- 单层碳库使用真实土层厚度和统一容重输入。
- 当前剖面与 CK 剖面必须完整覆盖 0-60cm，并在 20cm 处有边界。
- 秸秆情景只改变碳输入估算，不反向修改实测 SOC。
- 草稿 2 秒防抖保存，未完成草稿最多保留 7 天。
- 每条历史记录最多维护一份应用本地 PDF，用户另存或分享的副本不替代应用副本。
- 对比表格最多支持 5 条记录，当前雷达图只展示选择顺序中的前两条。
- 桌面宽屏（≥900px）使用左侧导航栏与参数/结果双栏；移动端使用底部导航栏，两端页面结构一致。
- 图表按"概览 / 剖面与侵蚀 / 管理情景 / 高级分析"四分区组织，每张图表先给出由当次数据推导的一句话结论。
- 报告页默认展示本地确定性评估摘要（离线、不经过模型）；AI 解读为可选次级功能。
- 恢复力评估页提供分层证据、侵蚀亏缺矩阵与情景覆盖对照（见业务契约"恢复力评估"节）。
- 应用名称统一为"碳盾 · SOC-Shield"。

## 6. 写作与界面说明规范

### 6.1 章节模板

功能章节尽量按以下顺序编写：

1. 功能目的。
2. 操作步骤。
3. 参数或控件说明。
4. 结果解释。
5. 注意事项。
6. 常见问题或下一步操作。

### 6.2 术语规范

- 首次出现的专业术语写出中文全称，并在括号中给出缩写或英文。
- 数值始终带单位，百分比和比例不能混写。
- “静态差异”“折算代理”“动态预测”必须区分使用。
- “土层键”只在科学附录或需要解释数据映射时使用，用户操作章节优先使用实际土层范围。
- 历史字段名 `netChange_20yr` 和 `netChange_100yr` 不得直接当作真实时间预测标题使用。

### 6.3 截图规范

- 截图是可选辅助材料，不是基础功能说明的必需内容。
- 基础操作优先使用文字、步骤、参数表、结果表和流程图说明。
- 若确实需要截图，必须来自当前版本应用，不使用旧版界面截图。
- 每张截图只突出一个操作目标，必须裁剪到相关区域，不能把整张长屏直接塞入 PDF。
- 截图必须设置最大宽度和最大高度，且使用 `break-inside: avoid`，不得溢出页面或把正文挤到下一页。
- 截图说明放在图片下方，说明“用户要做什么”，不描述源码实现。
- 涉及 API Key、个人路径或历史数据时，必须使用脱敏示例。
- 如果需要展示界面状态，应优先从当前源码运行并截取局部结果，而不是复用测试留档截图。
- 截图文件使用稳定名称，例如 `home-inputs.png`、`history-detail.png`。

### 6.4 表格与公式规范

- 参数表必须包含名称、单位、默认值、允许范围和用途。
- 结果表必须包含单位和正负值解释。
- 公式使用 Markdown 数学公式或清晰的等宽文本，HTML 和 PDF 中保持可读。
- 公式下方必须解释变量含义和适用范围。

## 7. 文档源文件与发布格式

### 7.1 单一源文件

Markdown 是说明书的唯一维护源。HTML 和 PDF 均由 Markdown 渲染生成，不分别维护两套正文。

允许少量内嵌 HTML 用于：

- 提示框。
- 折叠的补充说明。
- 图片标题或特殊布局。

不得把完整章节直接写成 HTML，以免内容难以比较、复用和导出。

### 7.2 发布产物

- HTML：支持目录跳转、搜索、响应式阅读和应用内复用。
- PDF：用于正式发布、离线阅读和归档。
- Markdown：用于版本控制、审阅和后续重新渲染。

HTML 和 PDF 应使用同一套公式和术语内容。图片属于可选资源；若使用图片，HTML 和 PDF 必须共享同一份经过裁剪的资源。PDF 渲染时必须验证中文字体、分页、表格宽度、图片清晰度和目录链接。当前说明书正文采用文字优先策略，不强制加入界面截图。

### 7.3 Ghostwriter 的职责

项目环境已安装 Ghostwriter。Ghostwriter 用于：

- 编写和修改 Markdown 源文件。
- 实时预览 Markdown、表格、代码块和基础图片。
- 人工检查章节结构、文字排版和阅读体验。

Ghostwriter 的 GUI 预览不作为唯一的发布校验依据。HTML 和 PDF 发布仍应使用固定、可重复执行的渲染工具链，以便在不同机器和不同版本之间得到一致结果。

推荐流程为：

```text
Ghostwriter 编写/预览
  -> 固定 Markdown 渲染器生成 HTML
  -> 固定 PDF 渲染器生成 PDF
  -> 人工复核 HTML/PDF 与 Ghostwriter 预览的一致性
```

### 7.4 渲染工具链选择

最终渲染工具需要单独验证以下能力：

- 中文字体和中英文混排。
- Markdown 表格、代码块和公式。
- 图片路径和图片清晰度。
- 目录、锚点和内部链接。
- HTML 响应式布局。
- PDF 分页、页眉页脚和长表格换页。

在工具链确定前，不将 Ghostwriter 的临时导出文件提交到源码目录，也不把某台机器的 GUI 配置当作发布配置。

当前已验证的工具链为：

- Ghostwriter `25.12.3`：Markdown 编写和人工预览。
- Node.js + `markdown-it` `14.1.0`：Markdown 到 HTML。
- Google Chrome `151.0.7922.137`：HTML 到 A4 PDF。

具体命令和脚本见 `docs/user-guide/tooling/README.md`。后续若更换渲染器，必须重新验证中文字体、目录、截图、公式和分页。

### 7.5 应用内复用

第一阶段只准备可复用的 Markdown 内容和静态 HTML 产物。应用内优先嵌入：

- 快速入门。
- 常见问题。
- 当前页面相关的帮助片段。

完整手册可通过应用内页面或系统浏览器打开。除非确有离线和统一交互需求，不优先在应用内实现完整 PDF 阅读器。

## 8. 版本和维护要求

- 说明书版本与应用版本分开记录。
- 说明书语义版本必须与应用语义版本一致；应用 build number 单独记录，不改变说明书主版本号。
- 计算口径、字段含义或页面行为发生变化时，必须更新说明书版本记录。
- 版本变更时先更新 `docs/user-guide/metadata.json`，再重新生成 HTML 和 PDF。
- 每次发布至少检查：参数表、可选插图、算法版本、草稿期限、PDF 行为、AI 配置和已知限制。
- 旧版本说明书保留在发布归档中，不覆盖当前版本正文。
- 文档不得包含真实 API Key、个人路径、机器配置或未验证的实验数据。

## 9. 验收标准

说明书发布前至少满足：

- 新用户只看快速入门即可完成一次默认计算。
- 完整指南能够解释所有首页输入项和主要结果项。
- 公式、单位、CK 参照和 0-60cm 剖面口径与当前代码和契约一致。
- 文档没有把静态差异描述成动态预测。
- 所有截图对应当前应用版本，且无敏感信息。
- HTML 可正常搜索、跳转和手机阅读。
- PDF 中文字体、目录、表格和图片显示正常。
- Android、Windows、AI、PDF、历史和 JSON 的平台差异均有说明。

## 10. 当前准备目录

说明书源码位于 `docs/user-guide/`，目录职责见该目录下的 `README.md`。生成的 HTML、PDF 和临时渲染文件不直接混入源码目录，发布产物应放入 `release/`，临时文件应放入 `temp/`。
